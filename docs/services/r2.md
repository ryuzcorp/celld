An `r2_buckets` binding gives your Worker object storage. Cello stores the objects in the [fleet bucket](../../guides/run-fleet.md) the node opened with `--bucket`, so R2 data has the durability of that object store. On a node without a fleet bucket, every R2 method fails.

## Example

The full runnable version is in [`examples/r2`](https://github.com/ryuzcorp/cello/tree/main/examples/r2).

<!-- cello-example: r2 -->

Declare the binding in `wrangler.json`:
```json
{
  "r2_buckets": [{ "binding": "FILES", "bucket_name": "example-files" }]
}
```

Read and write objects through `env.FILES`:

```js
export default {
  async fetch(request, env) {
    const key = new URL(request.url).pathname.slice(1);
    if (request.method === "PUT") {
      await env.FILES.put(key, request.body);
      return new Response(null, { status: 204 });
    }
    const object = await env.FILES.get(key);
    if (object === null) return new Response("Not found.", { status: 404 });
    return new Response(object.body);
  },
};
```

Run it with `cello dev`, then `PUT` a body and `GET` it back:

```sh
cello dev --port 9876
curl -X PUT --data-binary 'hello r2' http://127.0.0.1:9876/greet.txt
curl http://127.0.0.1:9876/greet.txt
```

## Use the API

Each binding has its own `bucket_name`. Cello stores key `<key>` as the object `r2/<bucket_name>/<key>`. A key holds 1 to 1024 bytes.

- `get(key, { range, onlyIf })` returns an `R2ObjectBody` with a streamed body, or `null`. A range is an `offset`, a `length`, a `suffix`, or a `Range` header.
- `head(key)` returns the object record without the body.
- `put(key, value, { httpMetadata, customMetadata, onlyIf })` takes a string, an `ArrayBuffer`, a typed array, a `Blob`, or a `ReadableStream`. A refused condition returns `null`. A streamed body that grows past 8 MiB becomes a multipart upload.
- `delete(keys)` removes one key or a list of up to 1000 keys in one call.
- `list({ prefix, delimiter, cursor, startAfter })` returns a page of objects. `startAfter` bounds the first page past a key; pass the `cursor` a listing answered you to continue it past exactly what the page consumed. Page every further listing with `cursor`: `startAfter` re-scans the whole prefix to find its bound on each page, and it silently drops keys where encoded and decoded sort orders disagree (see below).
- `createMultipartUpload(key)` returns a handle. `uploadPart(number, value)` sends one part, and `complete(parts)` assembles the object. A multipart upload lives on the node that opened it. A part that arrives before its predecessor waits in memory, up to 256 MiB, before Cello refuses a further part. A waiting part can be replaced; a part that already reached the object store cannot.

The object store keeps some keys in percent-encoded form: a key with a non-ASCII character, a control character, or one of `` `% \ { } ^ ` [ ] " < > ~ # | * ? ``. For example, `přehled.html` becomes `r2/<bucket_name>/p%C5%99ehled.html`. Each empty segment becomes `%`, so `photos/` becomes `r2/<bucket_name>/photos/%`, and `a/b`, `/a/b`, `a//b`, and `a/b/` are four different objects, as in Cloudflare R2. `list()` returns the decoded key but walks the objects in the encoded form's order, while `startAfter` compares decoded keys in UTF-8 byte order. Where the two orders disagree, a page still opens correctly but `startAfter` can skip keys, so prefer `cursor`.

A cursor is opaque: pass it back unchanged. An unseeded listing's cursor is the key it consumed, so `--cursor` also takes a plain key; a seeded listing's cursor carries its bound with it, so the continuation replays the first page's filter. `list()` fails when it reaches an object that another tool wrote with a percent-encoded key that is not UTF-8, such as `a%FF`.

An object that another tool wrote still reads through the binding. Its user metadata becomes its `customMetadata`, and its headers become its `httpMetadata`. Use `cello r2 put` to write the complete record.

## Know the differences from Cloudflare

| Area | Cello behavior |
| --- | --- |
| Storage | Each binding uses the fleet bucket under `r2/<bucket_name>/`. There is no public bucket URL, presigned URL, or S3 endpoint; put a Worker in front of the bytes to publish them. |
| Metadata | The five content headers are stored as headers. `customMetadata`, `cacheExpiry`, the checksums, and the storage class are stored together as one JSON value under the `cello-r2` user-metadata name (`cello_r2` on Azure Blob Storage, which refuses a hyphen in a metadata name). Objects a celld node wrote carry `celld-r2` (`celld_r2` on Azure) and read the same way; new writes use the new spelling. Cursors work under both spellings. |
| Versions | An object `version` equals its content ETag, so identical content produces the same version. |
| Unavailable | `ssecKey` and `jurisdiction` are unavailable. A conditional write cannot use a streamed body larger than 8 MiB. `createMultipartUpload()` takes no checksum. A multipart upload cannot resume on another node or after a restart, and Cello cannot replace a part the object store already holds. Out-of-order parts can use at most 256 MiB of memory, and completion cannot change the stored part order. |
| Legacy keys | cello 0.5.1 and earlier removed each empty segment from a key. An object such a version wrote under `photos/` stays under `photos`, and `list()` returns it as `photos`. |

The [Cloudflare compatibility](../reference/cloudflare-compat.md#services) page lists the runtime APIs and the unsupported services.

## Operate it

Manage objects without a running node. `cello r2` reads the fleet bucket directly, so a release pipeline can publish an object before it deploys the Worker:

```sh
cello r2 put example-files logo.png --path ./logo.png --bucket s3://my-fleet
cello r2 list example-files --prefix images/ --delimiter / --bucket s3://my-fleet
```

- `cello r2 get|head|put|delete|list` replaces `wrangler r2 object`. The bucket name is the `bucket_name` from the `r2_buckets` entry, not the binding name.
- With `--page`, `list` prints one page: objects with `httpMetadata` and `customMetadata`, plus `delimitedPrefixes`, `truncated`, and `cursor` (absent when the listing is complete). Without it, `list` prints one key per line. `--delimiter` rolls keys up into prefixes.
- Continue a truncated listing with `--cursor`, as the resume line says. `--after` bounds the first page past a key, and when both are given the cursor wins.
- A `get` or `head` of an absent key fails with exit code 1 and `no object "<key>" in r2 bucket "<bucket>"` on stderr. With `--json` it also prints `{"error":"not_found","bucket":"<bucket>","key":"<key>"}` on stdout first, so match the `error` field instead of the English message.
- `delete` of an absent key succeeds, as on R2. Run `cello r2 --help` for the full flag list.
