D1 is a SQL database that a Worker reaches through a binding. Cello gives each database its own SQLite file inside one cell. Read the [Cloudflare D1 documentation](https://developers.cloudflare.com/d1/worker-api/d1-database/) for the API.

## Run a minimal guestbook

This project creates an `entries` table on first request, inserts one row per `POST`, and lists the latest 20 rows. It runs unchanged on `cello dev` (verified with cello 0.2.1).

The full runnable version is in [`examples/d1`](https://github.com/ryuzcorp/cello/tree/main/examples/d1).

<!-- cello-example: d1 -->

```jsonc
// wrangler.jsonc
{
  "name": "d1",
  "main": "index.js",
  "compatibility_date": "2026-01-01",
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "guestbook",
      "database_id": "00000000-0000-0000-0000-000000000000"
    }
  ]
}
```

```js
// index.js
const SCHEMA = `CREATE TABLE IF NOT EXISTS entries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL, message TEXT NOT NULL, at INTEGER NOT NULL)`;

export default {
  async fetch(request, env) {
    await env.DB.exec(SCHEMA);
    if (request.method === "POST") {
      const { name, message } = await request.json();
      const written = await env.DB
        .prepare("INSERT INTO entries (name, message, at) VALUES (?, ?, ?)")
        .bind(name, message, Date.now())
        .run();
      return Response.json({ id: written.meta.last_row_id }, { status: 201 });
    }
    const { results } = await env.DB
      .prepare("SELECT id, name, message, at FROM entries ORDER BY at DESC LIMIT ?")
      .bind(20)
      .all();
    return Response.json({ entries: results });
  },
};
```

## Use the supported API

- `prepare(sql)` returns a statement, and `bind(...values)` returns a new statement that carries the values.
- `all()` returns `success`, a `results` array of row objects, and `meta`. `run()` is the same method under a second name.
- `first()` returns the first row or `null`, and `first(column)` returns one column of that row.
- `raw()` returns the rows as arrays, and `raw({ columnNames: true })` puts the column names in the first array.
- `batch(statements)` runs prepared statements in one transaction and returns one result per statement.
- `exec(sql)` runs one or more statements without parameters, such as a schema.

A `d1_databases` entry gives a `binding`, a `database_name`, and a `database_id`. Cello uses the `database_id` as the identity, or the `database_name` when the entry has no id. Two Workers that name one identity reach one database. Cello creates a database on first use, so a typo in the name opens an empty database instead of an error.

`bind()` checks each value. A number and a string pass, a boolean becomes `1` or `0`, and an `ArrayBuffer`, a typed array, or an array of byte numbers becomes a `BLOB`. Any other value throws `D1_TYPE_ERROR`. Cello binds the positional parameters `?` and `?NNN`.

Cello enforces these [D1 limits](https://developers.cloudflare.com/d1/platform/limits/): a statement of at most 100,000 bytes, at most 100 bound parameters, at most 100 columns in a table, and a string, a `BLOB`, or a row of at most 2,200,000 bytes.

A prepared statement that holds a second statement fails with `A prepared SQL statement must contain only one statement.` Use `exec()` or `batch()` for more than one statement. Both run in one transaction, so a failure rolls back the whole call.

Every statement goes to the node that owns the database cell, so each call costs one cell dispatch. Group related statements in one `batch()`, which costs one dispatch for all of them. The 100,000-row result cap does not apply to `first()`. An acknowledged write survives the loss of the owner node.

`withSession()` always selects the primary. `getBookmark()` returns `cello:primary`, `meta.served_by_primary` is always `true`, and `meta.served_by_region` is always `local`.

Application SQL cannot use `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `ATTACH`, `DETACH`, `VACUUM`, `load_extension()`, or a temporary table, index, trigger, or view. Cello allows the `fts5` and `fts5vocab` virtual tables, and it accepts the `PRAGMA` list in the [D1 SQL statement reference](https://developers.cloudflare.com/d1/sql-api/sql-statements/).

## Handle the differences from Cloudflare

| Area | Cello behavior |
| --- | --- |
| Result size | A binding result holds at most 100,000 rows or 32 MiB. |
| Non-UTF-8 text | A SQLite `TEXT` value that is not valid UTF-8 decodes with the replacement character U+FFFD, as workerd decodes it; the stored bytes do not change. Store arbitrary bytes in a `BLOB`. |
| Write capacity | One writer per database. Use more databases to increase write capacity. |
| Read replicas | None. `withSession()` always selects the primary, and `getBookmark()` returns `cello:primary`. |
| `last_row_id` / `changes` | A read-only statement reports both as `0`. Cloudflare reports the values the previous write left on the connection. |
| `prepare()` | Accepts exactly one statement. |
| `exec()` counting | Counts each statement. Cloudflare counts each input line. |
| `dump()` | Throws. The database is a SQLite file in your own bucket; export it with `cello d1 export`. |
| Forbidden SQL | `BEGIN`, `SAVEPOINT`, `ATTACH`, `VACUUM`, `load_extension()`, and temporary tables are unavailable (plus `COMMIT`, `ROLLBACK`, `DETACH`, temporary indexes, triggers, and views). |
| REST API / Time Travel | None. Use `cello d1` for SQL, migrations, and exports. |
| Large exports | An export builds the whole dump inside one cell call, so a database near the cap holds the owner isolate's event loop for the seconds the dump takes. Export fewer tables at a time when tail latency matters. |

The [Cloudflare compatibility](../reference/cloudflare-compat.md#services) page lists the runtime APIs and the unsupported services.

## Operate it

- `cello d1 execute DATABASE (--command SQL | --file PATH | --batch) --bucket s3://NAME` runs SQL through a live node. `--batch` reads a JSON array of statements from stdin and runs it as one transactional batch — D1's `batch()` semantics, one result per statement — printing one JSON array.
- `cello d1 export DATABASE --bucket s3://NAME` writes the database as SQL, read under one transaction on the owning node, so the dump is a single snapshot while the database takes writes. It prints to stdout, or to `--output`; repeatable `--table`, `--no-schema`, and `--no-data` narrow it, as `wrangler d1 export` does. Import a dump with `cello d1 execute DATABASE --file dump.sql`, which replays it in one transaction. One dump carries at most 32 MiB; export fewer tables at a time past that.
- `cello d1 migrations apply|list DATABASE --bucket s3://NAME` applies and lists migrations.
- Append `--local` to any `cello d1` subcommand to target the `cello dev` node instead of the fleet: the command reads the database identity from the project, then reaches the running dev node through `PROJECT/.cello/dev`. Pass the same `--state DIR` (or `CELLO_DEV_STATE`) when the node runs with an explicit state directory. The dev node must be running, and `--local` takes no `--bucket`, `--endpoint`, `CELLO_BUCKET`, or `S3_ENDPOINT`.
